## 1. 性能瓶颈从何而来

大数据量图表卡顿的根源通常有三类：

| 瓶颈 | 表现 | 对应策略 |
|------|------|----------|
| **渲染点数过多** | 渲染耗时长、首屏慢 | `large` / `lttb` / `sampling` / `dataZoom` |
| **单帧计算过重** | 页面假死、交互无响应 | `progressive` |
| **视觉开销过大** | GPU 负担重、掉帧 | 关闭动画 / 精简视觉样式 |
| **实例反复重建** | 频繁更新时累积开销 | 增量更新 |

## 2. 策略速查表

| 策略 | 核心原理 | 数据量 < 1万 | 1万~10万 | 10万~100万 | 100万+ |
|------|----------|:---:|:---:|:---:|:---:|
| `large` 大数据模式 | 轻量渲染管线 | 无收益 | 小收益 | 明显 | 必需 |
| `progressive` 渐进渲染 | 分帧让出主线程 | 无感 | 小收益 | 明显（交互） | 必需 |
| `lttb` 降采样 | 智能抽点至 5000 | 无收益 | 可选 | 推荐 | 推荐 |
| `sampling` 内置采样 | 按像素取平均 | 无收益 | 可选 | 推荐 | 推荐 |

## 3. 大数据模式 `large`

**原理**：ECharts 在 `large: true` 时切换到专门为大数据设计的渲染管线——跳过逐点样式计算、合并绘制命令、使用更紧凑的存储结构（折线/散点图有效）。

**适用**：折线图、散点图（柱状图不支持）。数据量超过 2,000 点后逐步显现收益，10 万点以上收益显著。

**注意**：
- `large` 模式下关闭了部分视觉能力（如符号样式、个别视觉通道），这是性能与视觉的权衡
- 与 `sampling` 配合时效果叠加

---

## 4. 渐进式渲染 `progressive`

**原理**：把一次完整渲染拆分为多个时间片（本平台每帧 500 点），通过 `requestAnimationFrame` 调度，每帧只渲染一部分。主线程不被单次长渲染阻塞，页面保持可交互，图表从第一帧起就开始呈现。

**适用**：所有图表类型。**它优化的是"交互流畅度"而非"总完成时间"**——这正是本平台"渲染耗时"指标采用首帧呈现时间而非 finished 总耗时的原因。

**注意**：
- 总渲染完成时间会略长于一次性渲染（分帧有调度空隙），但用户感知是"很快画出来了"
- 配合 `large` 使用效果最佳

---

## 5. LTTB 数据降采样 `lttb`

**原理**：Largest-Triangle-Three-Buckets 算法。将数据等分为 N 个桶（N = 目标点数），每个桶内以"与前一桶选中点的连线构成最大三角形"的准则选点，从而在**保留波形形状特征**的前提下将数据压缩到目标规模（本平台 5,000 点）。实现基于 `downsample-lttb` 库。

**适用**：所有图表类型，数据量大于 5 万时推荐。100 万点可压缩到 5,000 点，数据量直降 99.5%。

**注意**：
- 压缩后的点**不是均匀抽样**，峰值与谷值会被保留，这是 LTTB 相对"每隔 N 取一个"的核心优势
- 代价是精度损失：缩放到局部细节时不如原始数据精确（缩放场景建议关闭）
- 与 `dataZoom` 有取舍：dataZoom 保留全部数据只渲染可视区，LTTB 直接丢弃数据

---

## 6. 内置采样 `sampling`

**原理**：ECharts 折线图内置的 `sampling: 'lttb'`（数据量大时推荐）——在**绘制阶段**按当前像素宽度对数据取平均/取极值，只画"看得见的"点。数据不需要预先压缩，缩放时自动重采样。

**适用**：仅折线图。

**区别**：`sampling` 是 ECharts 内部的绘制期采样（保留全部原始数据）；`lttb`（策略 5）是渲染前的数据级压缩（丢弃数据）。两者原理相关、作用层面不同，可叠加使用。

---

## 7. 数据缩放 `dataZoom`

**原理**：`dataZoom` 组件把图表变成"视口 + 滚动条"结构，**只渲染可视窗口内的数据**。本平台初始显示前 20% 数据，可通过底部缩放条浏览其余数据。

**适用**：所有图表类型。数据量越大收益越显著——100 万点只渲染 20 万点，首屏渲染提速约 5 倍。

**注意**：
- 缩放/平移时需要重算可视区间，拖拽缩放条时会有短暂的渲染开销
- 与 `lttb` 联用时数据先压缩再缩放，双保险

---

## 8. 关闭动画

**原理**：大数据渲染时，动画插值会触发持续的 `requestAnimationFrame` 重绘，占用主线程与 GPU。`animation: false` 让图表首帧直接呈现。

**适用**：所有图表类型。数据量超过 `animationThreshold`（默认 2,000）时 ECharts 会自动禁用动画，**手动关闭动画在 1,000 点以下的小数据场景仍有收益**（避免初始动画的 300ms 等待）。

---

## 9. 精简视觉样式

**原理**：移除 `areaStyle` 渐变填充、`shadowBlur` 阴影等重样式，改用纯色。阴影与渐变在 Canvas 上需要逐像素计算，是渲染与合成阶段的主要开销之一。

**适用**：所有图表类型。未优化侧的红色图表刻意保留了这些重样式，代表真实项目中"默认写法"的最坏情况。

---

## 10. 增量更新模式

**原理**：每次点击"应用配置"时，若图表类型 / 渲染器 / 数据格式未变化，则复用现有图表实例调用 `setOption(option, true)` 全量替换，**避免 `dispose()` + `init()` 的销毁重建开销**（销毁重建需要重新初始化渲染器、事件系统、内存分配）。

**适用**：所有图表类型，仅"一次性加载"模式生效（分片加载每次都从空数据开始，不适用）。

**注意**：收益在"连续多次更新"场景最明显；频繁切换图表类型/渲染器时该策略自动失效（需要重建）。

## 11. 策略组合建议

| 场景 | 推荐组合 |
|------|----------|
| 默认演示（1 万点） | `large` + `progressive` + `dataZoom` |
| 10 万点折线图 | `large` + `progressive` + `sampling`（或 `dataZoom`） |
| 100 万点折线图 | `large` + `progressive` + `lttb`（或 `dataZoom`） |
| 100 万点柱状图 | `progressive` + `dataZoom`（柱状图无 large） |
| 频繁切换配置对比 | 上述任意组合 + `增量更新` |
| 交互流畅优先 | `progressive` + `large` + Tooltip 触发改为 `click` |

> 组合不是越多越好：`lttb` 与 `dataZoom` 存在功能重叠，同时开启时数据先被压缩、可视区再缩小，精度损失叠加，按需取舍。

## 12. 性能问题排查清单

| 现象 | 排查方向 |
|------|----------|
| 首屏渲染慢 | 数据量是否过大？开启 `large` / `dataZoom` / `lttb` |
| 页面假死无响应 | 是否缺少 `progressive`？单帧渲染过长 |
| 交互卡顿掉帧 | Tooltip 是否为 `mousemove`？改为 `click`；是否关闭动画 |
| 内存持续增长 | 是否频繁销毁重建实例？开启增量更新；改用 TypedArray |
| SVG 渲染明显慢 | 大数据下 SVG 天然弱于 Canvas，切换渲染器 |
| 柱状图很卡 | 柱状图无 `large` 支持，依赖 `dataZoom` + `progressive` |
