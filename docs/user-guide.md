# ECharts 性能优化对比实验室 · 操作指南

> 一个用于直观对比 ECharts 图表在 **未优化** 与 **应用多种优化策略** 后性能差异的交互式演示平台。
> 左右并排两个图表，使用完全相同的原始数据，通过实时性能指标（渲染耗时 / FPS / 内存）量化对比优化效果。

## 1. 启动与访问

### 环境要求

- **Node.js** ≥ 18（推荐 20+）
- **Chrome / Edge** 最新版（内存指标仅 Chrome 系浏览器支持）
- 无需后端服务，纯前端应用

### 安装与运行

```bash
# 安装依赖（首次运行执行一次）
npm install

# 启动开发服务器（自动打开浏览器 http://localhost:5173）
npm run dev

# 生产构建
npm run build

# 本地预览构建产物
npm run preview
```

## 3. 数据控制区

| 控件 | 说明 |
|------|------|
| **数据量滑块** | 范围 1,000 ~ 10,000,000。采用分段映射：1k~100k 步长 1,000；100k~1M 步长 10,000；1M~10M 步长 100,000 |
| **数值输入框** | 滑块右侧的数字输入框，可直接输入精确数据量（自动约束在 1,000~10,000,000） |
| **快捷按钮** | `1k` `10k` `100k` `1M` `10M`，一键切换常用数据量 |
| **数据格式** | `普通 Array`：嵌套二维数组；`TypedArray`：扁平 Float64Array（内存占用更低、解析更快） |
| **加载模式** | `一次性加载`：全部数据一次渲染；`分片加载（流式）`：每批 5,000 条通过 `appendData` 逐步追加，界面保持可交互 |
| **生成数据** | 使用新的随机种子重新生成数据（波形趋势不变，噪声随机），同时刷新两个图表 |

> 💡 **提示**：切换到 10M 数据量时，数据生成约需 1~2 秒，期间图表显示加载动画，属正常现象。

## 4. 优化策略区

> 以下策略 **仅作用于右侧图表**，左侧始终保持无优化状态。所有策略可自由组合，实时叠加。

| 策略 | 作用 | 适用图表 | 效果预估 |
|------|------|----------|----------|
| ☐ 大数据模式 (`large`) | 数据量超过阈值后切换轻量渲染管线，跳过逐点样式计算 | 折线图 / 散点图 | 渲染速度提升 2~5 倍 |
| ☐ 渐进式渲染 (`progressive`) | 分帧渲染（每帧 500 点），避免单帧阻塞主线程 | 全部 | 交互响应提升 50%+ |
| ☐ 数据降采样 (LTTB) | 智能采样至 5,000 点，保留波形趋势特征 | 全部 | 数据量直降 90%+（数据 > 5 万时推荐） |
| ☐ 内置采样 (`sampling`) | 绘制前按像素宽度取平均，只画可见分辨率下的有效点 | 仅折线图 | 大数据折线渲染大幅加速 |
| ☐ 数据缩放 (`dataZoom`) | 只渲染可视区域，初始显示前 20% 数据 | 全部 | 首屏渲染提速 5~10 倍 |
| ☐ 关闭动画 | 避免大数据下的插值计算与重绘 | 全部 | 首帧直接呈现 |
| ☐ 精简视觉样式 | 移除阴影 / 渐变，改用纯色 | 全部 | 降低 GPU 与 CPU 双重开销 |
| ☐ 增量更新模式 | 数据更新时复用图表实例（`setOption` 全量替换），避免销毁重建 | 全部 | 多次更新时整体耗时显著降低 |

> ⚠️ **注意**：
> - 不适用于当前图表类型的策略会自动忽略，并在右侧优化标记中隐藏
> - `增量更新模式` 仅在"一次性加载"下生效（分片加载每次都从空数据开始追加）
> - 右侧图表标题下方会显示当前生效的策略标记，如 `+large +progressive +dataZoom`

## 5. 交互控制区

| 控件 | 选项 | 说明 |
|------|------|------|
| **渲染器** | `Canvas` / `SVG` | 切换整个渲染管线。大数据量下 Canvas 明显更快；SVG 适合小数据量的矢量展示 |
| **图表类型** | `折线图` / `散点图` / `柱状图` | 不同图表对优化策略的敏感度不同：折线图最直观，柱状图大数据下压力最大 |
| **Tooltip 触发** | `mousemove` / `click` | `mousemove` 高频触发重绘；`click` 按需触发，大数据下 FPS 显著提升 |

## 6. 操作按钮

| 按钮 | 功能 |
|------|------|
| **⚡ 应用配置** | 应用当前所有设置，重新生成/获取数据并渲染两个图表（两个图表同时显示加载动画） |
| **↺ 重置为默认** | 恢复所有控件到默认状态（10,000 点 / 普通数组 / 一次性加载 / 预设 `large + progressive + dataZoom` / Canvas / 折线图），并自动应用 |
| **导出 CSV** | 导出当前左右性能指标对比为 CSV 文件（带 UTF-8 BOM，Excel 可直接打开） |
| **导出 JSON** | 导出完整结构化报告（含配置、左右指标、改善幅度） |
| **导出图片**（图表右上角） | 将单个图表导出为 2 倍分辨率 PNG 图片 |

## 7. 性能指标解读

每个图表下方实时显示：

| 指标 | 含义 | 说明 |
|------|------|------|
| **数据点** | 当前参与渲染的数据点总数 | 开启 LTTB 降采样后，右侧数值会远小于左侧 |
| **渲染耗时** | 首帧呈现时间：`setOption` 到第一次绘制完成（毫秒） | 一次性渲染 = 全量完成时间；progressive 分帧渲染下体现"快速首屏"优势；分片加载模式为全部批次完成的总耗时 |
| **FPS** | 最近 500ms 窗口的平均帧率 | 由 stats.js 面板（图表右上角）+ 指标卡数值双重展示 |
| **内存增量** | 本次渲染的内存增量（渲染前后 JS 堆差值，MB） | 仅 Chrome/Edge 支持，其他浏览器显示 `--` |
| **加载方式** | 一次性 / 分片加载（含进度） | 分片模式显示"已加载/总量" |
| **优化标记** | 右侧图表生效的策略列表 | 悬停可查看每个策略的原理说明 |

### 对比高亮规则

- 右侧指标 **优于左侧 30% 以上** → 数值变绿并显示 **▲**
- 右侧指标 **劣于左侧 30% 以上** → 数值变红并显示 **▼**
- 鼠标 **悬停任一指标** 可查看该指标的含义与相关策略说明

## 8. 推荐操作流程

### 场景一：快速了解优化效果（默认）

打开页面即可看到默认对比：10,000 点折线图，右侧应用了 `large + progressive + dataZoom`。
观察右侧的渲染耗时与 FPS 相对左侧的提升（绿色 ▲ 标记）。

### 场景二：探索单个策略的效果

1. 在"优化策略区"只勾选一个策略（如 LTTB）
2. 将数据量调到 **100 万点** 以上（LTTB 优势最明显）
3. 点击"应用配置"，观察：
   - 右侧"数据点"从 1,000,000 降为 5,000
   - 右侧渲染耗时大幅下降、FPS 提升
4. 取消勾选再看一次，对比同一配置下的差异

### 场景三：分片加载体验

1. 加载模式选择"分片加载（流式）"
2. 数据量调至 100 万点，点击"应用配置"
3. 观察图表底部进度条逐步推进、数据逐渐呈现，期间页面始终保持可交互
4. 配合右侧勾选 `progressive`，右侧追加过程会更流畅

### 场景四：内存对比（TypedArray）

1. 数据格式切换为 `TypedArray`，数据量 100 万点，应用配置
2. 对比普通 Array 模式下的"内存增量"指标，观察 TypedArray 带来的内存下降

### 场景五：tooltip 触发方式对比

1. 图表类型选"散点图"，数据量 10 万点以上，Tooltip 触发选 `mousemove`
2. 在图表上移动鼠标，观察 FPS 下降
3. 切换为 `click` 后应用，移动鼠标不再触发重绘，FPS 恢复

### 场景六：导出报告

1. 调整到目标配置并应用
2. 点击"导出 CSV"或"导出 JSON"保存报告
3. 点击图表右上角"导出图片"保存对比截图

## 10. 常见问题（FAQ）

**Q1：内存指标显示 `--`？**
内存监控依赖 Chrome 的 `performance.memory` API，请使用 Chrome 或 Edge 打开；其他浏览器（Firefox/Safari）不支持该 API。

**Q2：10M 数据量时页面卡顿/假死？**
这是预期现象——10M 点本身就是极端压力测试场景。建议：
- 数据量在 100 万以下体验最佳
- 大数据量务必勾选 `large + dataZoom`（或 LTTB）
- 右侧优化图表在 10M 下依然可以流畅，左侧无优化图表卡顿正是对比的意义所在

**Q3：分片加载时柱状图是"模拟"分片？**
柱状图不支持 ECharts 的 `appendData` 接口，程序自动回退为"分批 `setOption` 累积数据"，加载方式会显示"分片加载(模拟)"，效果一致。

**Q4：为什么勾选了 `large` 但优化标记里没有？**
`large` 模式仅适用于折线图和散点图。当前是柱状图时该策略会被自动忽略（策略不适用），可切换图表类型后生效。

**Q5：左侧图表为什么比右侧明显卡顿？**
左侧未应用任何优化，且刻意保留了阴影、渐变、动画等高开销样式（未优化侧样式代表真实项目中最常见的"默认写法"），这正是演示的目的——让优化收益直观可见。

**Q6：切换渲染器到 SVG 后右侧也变慢了？**
SVG 渲染器本身在数据量较大时性能低于 Canvas，这是 SVG 的技术特性。切换渲染器是全局设置（两个图表同时生效），可回到 Canvas 并配合其他策略继续对比。

**Q7：增量更新模式看起来没区别？**
增量更新（复用实例）的收益在"连续多次更新"时最明显：每次点击"应用配置"都会复用实例，避免了销毁重建的开销。数据量越大（如 100 万点），差异越显著。

**Q8：数值输入框输入的值与滑块位置不一致？**
滑块采用分段映射，输入框允许任意 1000~1000 万之间的整数；输入后滑块会吸附到最近的有效档位，以输入框数值为准。

## 11. 性能测量方法说明

| 指标 | 测量方式 |
|------|----------|
| 渲染耗时 | `performance.now()` 记录 `setOption` 调用时刻，监听 ECharts `rendered` 事件计算首帧呈现时间（不用 `finished` 是因为 progressive 分帧渲染的总完成时间天然更长，无法体现"快速首屏"优势）；分片模式记录所有批次追加完成 + 最后一次渲染完成的总耗时 |
| FPS | 基于 `requestAnimationFrame` 统计 500ms 窗口内的帧数，同时挂载 stats.js 面板实时显示 |
| 内存 | 渲染前 / 渲染后各触发一次 GC（分配约 64MB 临时对象触发 scavenger），再读取 Chrome `performance.memory.usedJSHeapSize`，计算**差值**作为本次渲染的内存增量（负值钳制为 0，小于 0.1MB 显示 `< 0.1 MB`）。不用绝对值是因为堆内存是整个页面进程的，先渲染的左侧数据仍在堆中，绝对值无法公平对比；V8 的堆统计只在 GC 后刷新，读数前不强制 GC 则差值恒为 0 |
| 数据点 | 普通数组取 `length`；TypedArray 取 `length / 2`（每点 2 个数字） |

> 测量建议：性能数据受机器负载影响，做严谨对比时建议在安静环境下多次测量取平均值。
